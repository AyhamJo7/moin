## Findings

### CRITICAL

None.

### HIGH

None. M1 becomes HIGH as soon as an HTTP invitation-acceptance route, or any `billing:manage` / `integrations:manage` route, ships.

### MEDIUM

- **M1 (P06.07.01, PLAN L1043-1044 "Connect/disconnect integrations: Admin ✘", "Billing: Admin ✘"; QG-09): admins can issue invitations that confer `billing_admin` / `integration_admin`, capabilities they do not hold themselves.** `apps/server/src/modules/identity-access/http/members.controller.ts:104-110` only escalates the required capability for `role === 'owner'`. `apps/server/src/modules/identity-access/domain/invitations.ts:88-99` (`checkedPermissions`) checks only that the permission names are valid. `domain/roles.ts:131-147` has no grant-authority capability. **Reproduced:** an admin `POST /api/members/invite {role:'admin', permissions:['billing_admin','integration_admin']}` → 201. The stored invitation is `{"role":"admin","permissions":["billing_admin","integration_admin"]}`, and store-level `acceptInvitation` as `moin_app` mints that membership, for which `may(...,'billing:manage')` and `may(...,'integrations:manage')` both return true. An admin can also invite `staff` with `billing_admin` (201). **Exploit path:** the admin invites a mailbox they control. Once acceptance has an entry path, that identity holds billing/integration powers that the matrix denies to admins. Not reachable end to end today, because there is no HTTP accept route (`members.controller.ts:23-27`) and no billing/integration routes yet. **Fix:** require `may(caller, 'billing:manage')` to grant `billing_admin` and `may(caller, 'integrations:manage')` to grant `integration_admin` (in effect owner-only, or holders of the permission if the founder prefers). Enforce it in the controller and in `app.accept_invitation`/issuance against the issuer's membership at accept time. PLAN is silent on grant authority, so the founder should confirm the rule. **Failing-test sketch:** admin invites `{role:'admin', permissions:['billing_admin']}` → expect 404 (or 403) and no `invitations` row. The same call as owner → 201.
- **M2 (P06.07.04 robustness, lock order on a control path): concurrent ownership changes deadlock and return 500.** `members.controller.ts:334-361` (transfer: promote, then demote own row) racing `members.controller.ts:267-300` (remove: `FOR UPDATE` on the target, then DELETE). The `memberships_last_owner` AFTER ROW trigger takes the per-org advisory lock only after the row locks are held (`0029_owner_invariant.sql:46`). **Reproduced** 3/10 iterations (and once in run 1): `40P01 deadlock detected: Process A waits for ShareLock on transaction …; Process B waits for ExclusiveLock on advisory lock` → HTTP 500. Postgres aborts one side, so the invariant held every time. The `0029` header (lines 14-16) says "opposing transfers queue per org", which is not what happens. **Fix:** take `pg_advisory_xact_lock(hashtext('last-owner:'||org))` as the first statement of every membership/role/status-changing transaction (disable, remove, transfer, `disableAccount`, enable), before any `FOR UPDATE`. Map `40P01`/`40001` to a retry or a 409. **Failing-test sketch:** loop 20× `Promise.all([transfer A→admin, B remove A])` and assert no 5xx and ≥1 effective owner (`/tmp/moin-review/claude-sec03-rbac/zz-claude-sec03-race.integration.test.ts`, "transfer racing removal").
- **M3 (evidence integrity, EV-P06-053, control-path mutation proof): the recorded B1/B2 mutants SURVIVE on current main.** They mutate `app.reject_last_owner_loss` in `0017_last_owner_protection.sql`, a body that `0029_owner_invariant.sql:21` later replaces with `CREATE OR REPLACE`. The mutants are therefore equivalent and the killing test passes with them applied (`/tmp/moin-review/claude-sec03-rbac/mutants.log`, B1 and B2 exit=0). B1 and B2 are also the same find/replace (`docs/verification/session-mutation-manifest.json:1082-1107`). The protection itself is proven by B1'/B2' on 0029 and B5 on 0030 (all KILLED). **Fix:** retarget B1/B2 to `0029_owner_invariant.sql` and add a 0030 mutant (`IF v_owners = 0` → `IF false`, killed by `packages/db/src/owner-invariant.integration.test.ts`). Then re-record EV-P06-053's mutation row.
- **M4 (P06.07.05 "every route × every role"): the matrix is generated from a hand-kept controller list, not from the mounted route table.** `apps/server/src/modules/identity-access/rbac-real-routes.integration.test.ts:233-238` (`CONTROLLERS = [Members, Recovery, Support, Auth]`) and `:283-304` (`EXPECTED`). Current main also serves `POST /api/tasks/:id/complete`, `GET /api/tasks/:id` (`apps/server/src/modules/work/http/tasks.controller.ts:57-77`) and `GET /api/today` (`work/http/today.controller.ts:41-47`). They are undecorated (no `@Require`), so the pin's own rule "no undecorated product route" (`:364-369`) would reject them if they were in scope, and a new controller in any module escapes the pin entirely. Task role behaviour _is_ tested separately (`work/owner-completes-callback.integration.test.ts:722+`, 22/22 pass), but not by the matrix. **Fix:** derive `ROUTES` from the booted `ApiRootModule` (`app.getHttpAdapter().getInstance().printRoutes()` or Nest `DiscoveryService`), require every non-public route to appear in `EXPECTED`, and give Work routes explicit rows (an explicit `@Require('tasks:act')`-style marker, or an allowlist entry naming the service-level check).

### LOW

- **L1: a last-owner refusal inside `POST /api/recovery/disable-user` is not mapped, so the client gets 500 instead of 409/404.** `apps/server/src/modules/platform/member-queries.ts:93-125` lets `23000` from `users_last_owner` propagate. Reproduced in 7/10 membership-disable vs account-disable races (`200,500`). The invariant holds and the body is Nest's generic 500, so nothing leaks. Fix: catch `23000` like `members.controller.ts:225-229`.
- **L2: the matrix tests cover roles but not the additive-permission holders.** There are no admin+billing_admin or staff+integration_admin rows in `rbac-real-routes`. The probe shows staff+both permissions still get 403 on user management. Add permission-holder rows once `billing:manage` / `integrations:manage` routes exist.
- **L3: the xsuite hard-codes the Keycloak issuer** (`apps/server/src/modules/xsuite/cross-tenant.integration.test.ts:83`) instead of reading `TEST_OIDC_ISSUER_URL`. A postgres-only private stack therefore fails one test for environmental reasons, which weakens standalone reproducibility of EV-P06-059.
