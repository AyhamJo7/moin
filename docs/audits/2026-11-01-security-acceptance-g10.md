## Findings

No CRITICAL or HIGH finding is reachable on main, because no runtime role can EXECUTE any support read (verified: `proacl` of all four read functions is `{moin_migrator=X/moin_migrator}`). Every MEDIUM below becomes HIGH on the day P06.11.01 grants EXECUTE to `moin_support_ro`. Treat them as preconditions for that change.

### MEDIUM

- **M1. The runtime role can forge, resurrect and extend grants with plain DML, with no audit row. Tag: INV-10, P06.11.02.**
  `packages/db/migrations/0022_support_grants.sql:67` grants `SELECT, INSERT, UPDATE ON support_access_grants TO moin_app`. No trigger protects the table. The 72 h CHECK at `:51` is relative to the writable `created_at`.
  Proof (`p1.log`, as `moin_app`, tenant context set): direct INSERT of `rogue-op`, then `UPDATE ... SET revoked_at = null, created_at = now()+1000 days, expires_at = now()+1000 days 72 h` succeeded. The grant was live about 1000 days out, with 0 audit rows. In the simulated activation, `support_read_memberships(org,'rogue-op',…)` returned the roster.
  Fix: revoke INSERT/UPDATE on `support_access_grants` from `moin_app` (the controller only needs the DEFINERs plus SELECT for listing). Alternatively, add a BEFORE UPDATE trigger that makes `revoked_at` one-way and `created_at`/`expires_at`/`operator_subject`/`scope` immutable, and set `created_at` from `clock_timestamp()` in the DEFINER only. Pin the ACL in the catalog check.
- **M2. The per-tenant cap of 5 (0028 M1 fix) is a check-then-insert race. Tag: P06.11 hardening.**
  `0028_support_grant_hardening.sql:98-106` runs an unlocked `count(*)` at READ COMMITTED.
  Proof (`probe-http.log` P4): 12 parallel `POST /api/support/grants` from one owner session returned 10×201 and 2×500, leaving **10 live grants**.
  Fix: take `pg_advisory_xact_lock(hashtext('support_grant:'||org))` or `SELECT … FROM organisations WHERE id = org FOR UPDATE` before the count. Add a parallel-create regression test.
- **M3. The documented maximum `hours: 72` always fails with HTTP 500.** `0028:117` sets `expires_at = clock_timestamp() + 72 h`, but `created_at` defaults to `now()` (transaction start), so `support_grant_max_72h` (`0022:51`) is violated by the elapsed microseconds.
  Proof: P2 → 500, and `p1.log` shows the check-constraint error.
  This fails closed, but the controller (`support.controller.ts:59` allows `max(72)`) turns a valid request into an unhandled 500. The quota refusal (`P0001`) also surfaces as 500. Fix: insert `created_at = clock_timestamp()` explicitly (or compute both from one value) and map `P0001`/`23514` to a 4xx problem.
- **M4. Supersede revokes earlier grants silently. Tag: INV-10.** `0028:109-113` sets `revoked_at` on prior live grants for the same operator+scope without a `support.grant_revoke` audit event.
  Proof (P3): grant 1 is revoked, and the audit trail shows only two `support.grant_create` rows.
  Fix: emit one `support.grant_revoke` (or `support.grant_supersede`) audit event per superseded row, in the same transaction.
- **M5. Read audits do not carry a trustworthy operator identity. The emergency path authenticates nothing. Tag: P06.11.04.** `0022:226-230`, `0028:159-165`: `actor_id` is the caller-supplied `p_actor_id` and `operator_subject` is never written. The emergency row has no target and no subject.
  The 0028 H2 "binding" compares `split_part(p_incident_ref,':',2)` with the caller's own `p_operator_subject`.
  Proof (`p2.log`): `support_emergency_read_memberships(orgB,'anyone',…,'op:anyone:abcd')` returned the roster of org B, and the audit row's actor is a random UUID.
  Fix (before any EXECUTE grant): derive the operator identity from a trusted session (P06.11.01) inside the definer, write the operator subject (or its opaque id) and the grant id into the audit row, and require a verified incident record for the emergency path.

### LOW

- **L1.** The P06.11.05 gate tests prove a copy of the predicate (`support.integration.test.ts:363-372`) and a lock-ordering shape that the current 0028 body no longer uses (`:400-474`). They would stay green if `live_support_grant` regressed. Replace them with tests that call `app.live_support_grant` (and, after P06.11.01, the reads as `moin_support_ro`).
- **L2.** Unpaginated roster/invitation reads (`0022:231,275`) remain as recorded in EV-P06-074 L2.
