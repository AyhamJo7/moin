### What holds (probe results on main)

- Missing header, header without cookie, header mismatching cookie, duplicate `__Host-moin_csrf` cookie (cookie-tossing shape), repeated `x-csrf-token` header, lower-case `__host-` cookie variant: all 403 `/problems/csrf-required`.
- Origin `null`, foreign, other port, other scheme, userinfo, `evil.localhost` subdomain, `localhost:3000.evil.example` suffix, empty, and repeated Origin (own+evil and evil+own): all 403, even with a valid token. Same-origin variants (trailing slash, upper-case host) admitted (correct normalisation).
- Method override (`X-HTTP-Method-Override`, `X-Method-Override`, `X-HTTP-Method`, `?_method=`) does nothing (404). PUT/PATCH/DELETE/OPTIONS/HEAD on mutation routes: 404 (not routed). No CORS is enabled anywhere, and there is no method-override plugin.
- Cross-site "simple" content types (`text/plain`, `application/x-www-form-urlencoded`) without a token: 403. `multipart/form-data`: 415.
- Route inventory (Fastify `printRoutes` on IdentityAccess + Work + CallSimulator + Health, i.e. the ApiRootModule graph): there are 14 POST routes. 13 are cookie-authenticated, and every one of them answered a token-less POST with 403 csrf-required before its handler ran (the staff target stayed `active`). The 14th, `/api/dev/simulated-calls`, is bearer-token only, uses no cookie, and is inert unless configured. GET routes (`/api/today`, `/api/tasks/:id`, `/api/support/grants`, health, login/callback) change no business state.
- `SameSite=Lax` and `__Host-` on both cookies, so no cross-site subrequest carries the session cookie at all. That is a third independent layer.

### HIGH

### MEDIUM

- **M1 (P06.06.06 / PLAN Security Architecture "CSRF" row, QG-09): the "synchronizer token" is an unsigned double-submit cookie that is not bound to the session.** `apps/server/src/modules/identity-access/http/csrf.ts:86-121` (`verifyCsrf` compares header to cookie only), `apps/server/src/modules/identity-access/http/auth.controller.ts:231-237` (random token, no server state). Probe result: the victim's `__Host-moin_sid` sent with _another session's_ csrf cookie+header pair is admitted (200), and so is an arbitrary never-issued pair (`Z`x43 in both cookie and header, 200). That makes it a different control from the one PLAN names. A synchronizer token is per-session and kept server-side. The code comment at `csrf.ts:10-13` still claims the token "is never a cookie". **Exploitability today:** none found. The bypass needs the attacker to write a `__Host-moin_csrf` cookie into the victim's jar, and browsers refuse that from sibling subdomains and over plain http (`__Host-` + `Secure`). An attacker with same-origin script already wins regardless. So this is a spec-conformance and defence-in-depth gap, not an open hole. **Fix (either one):** (a) bind the token to the session, e.g. `csrf = base64url(HMAC(AUTH_LOCAL_TOKEN_KEY, session_token_hash))`, and verify it against the resolved session (signed double-submit, OWASP-recommended). Test: a victim sid plus another session's matching pair → 403. (b) The founder records an ADR that amends PLAN L1063 to "`__Host-` double-submit". Loosening the PLAN wording is the founder's call.

### LOW

- **L1 (PLAN L1063 "strict `Origin` verification"): an absent Origin passes, and Referer is ignored.** `csrf.ts:94-97,114`. Probe: no Origin plus a foreign `Referer` plus a valid token → 200. Every current browser sends Origin on POST, so this only admits non-browser clients that already hold the token. Fix: when Origin is absent, check `Sec-Fetch-Site` (refuse `cross-site`) or `Referer`. This was already raised as EV-P06-068 FIX-8 "s3 sec L2" and is still open on main.
- **L2: CSRF is judged after `contexts.resolve(..., 'mutate')`.** `apps/server/src/modules/identity-access/http/session-membership.guard.ts:189` vs `:203-246`. A rejected forged POST still takes the session FOR UPDATE / FOR SHARE locks and slides `idle_expires_at` (`0016_session_revocation.sql:324-335`). That is the same effect any top-level GET navigation already has, so the impact is negligible. Raised as EV-P06-068 FIX-8 and still open. Fix: run `verifyCsrf` first, keeping 401 ahead of 403 by checking only that the cookie is present.
- **L3: `APP_ORIGIN` is not cross-checked against the `OIDC_REDIRECT_URI` origin.** `apps/server/src/config/env.ts:410-440` / `:311-327`. A mismatched deployment would make every mutation fail (closed) or point the check at the wrong origin. Raised as EV-P06-068 FIX-9 and still open. Fix: superRefine equality plus a unit test.
- **L4: no test pins "every non-GET cookie route goes through `SessionMembershipGuard`".** The probe inventory above shows all 13 do today, but a future controller that mounts only `RequireRoleGuard` or a custom guard would ship without CSRF and no test would fail. Fix: walk the Fastify route table in an integration test and require each POST route to answer 403 csrf-required, or to sit on an explicit allowlist (`/api/dev/simulated-calls`). Also raised as FIX-9.
- **L5 (evidence accuracy): EV-P06-051 says 5/5 C variants, but C1 and C2 are the same find/replace** (`docs/verification/session-mutation-manifest.json`, ids `C1-missing-token-accepted` and `C2-forged-token-accepted`). There are 3 distinct CSRF mutants plus the guard-skip mutant. The 4/4 kill result itself reproduces on main.
