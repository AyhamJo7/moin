## Critical

**C1 — Live Stripe secret key hardcoded in source.** `packages/integrations/src/stripe.ts:2`. Violates INV-15 ("secrets only in AWS Secrets Manager by ARN") and `.claude/rules/integrations.md`. Any clone/CI log/PR diff now has a `sk_live_...` string in git history permanently. Failure mode: key is scraped by a bot within minutes of a public push or a contractor with repo read-access exfiltrates it; Stripe account is fully compromised (charges, payouts, customer PII). Fix: remove the literal, load from Secrets Manager by ARN via the (not-yet-built) config loader, rotate the key immediately, and add a pre-commit/CI secret-scan gate that fails on `sk_live_`/`sk_test_` patterns in `packages/**`.

**C2 — Tenant context taken from a client-supplied header with no session/auth derivation.** `apps/server/src/modules/contacts/http/contacts.controller.ts:12`. Violates INV-02 ("tenant context derived server-side only"). Failure mode: any caller sets `x-org-id: <victim-org>` and the handler happily runs `withTenant` for that org — RLS is honored but the *tenant selection itself* is forged, so it's a complete horizontal privilege-escalation / cross-tenant data read with zero auth. Fix: derive `organisationId` from the authenticated session/JWT established upstream (auth middleware), never from a request header; reject requests without a valid server-side session.

**C3 — SQL built by string interpolation of user input.** `apps/server/src/modules/contacts/http/contacts.controller.ts:16`. Violates INV-02's explicit ban and the global "parameterized queries only" standard. `req.query.q` flows unescaped into `ILIKE '%${...}%'`. Failure mode: classic SQL injection — `q = %' UNION SELECT id,name,phone FROM contacts--` or, worse, a stacked statement resetting `app.organisation_id` mid-transaction, defeating the RLS boundary `withTenant` was just built to enforce. Combined with C2 this is a full tenant-isolation break. Fix: parameterize (`WHERE name ILIKE '%' || $1 || '%'` with `[req.query.q]`), and validate `q` with a Zod schema at the boundary (also closes the missing-input-validation gap — `SearchQuery` is an untyped-at-runtime interface, not a validated model).

**C4 — Import job writes to `contacts` without setting tenant context.** `apps/server/src/modules/contacts/jobs/import-contacts.job.ts:12-15` calls `pool.query` directly instead of the `withTenant` helper added in this same diff (`packages/db/src/tenant.ts`). Under INV-01 (FORCE RLS, `NOBYPASSRLS` runtime role), an INSERT policy will reference `current_setting('app.organisation_id')`; with the GUC unset this insert either hard-fails for every nightly run (feature is dead on arrival) or, if any policy is permissive, writes rows without server-verified tenant scoping. Either way it contradicts the very invariant the sibling `withTenant` utility exists to enforce, in the same PR. Fix: wrap the loop in `withTenant(pool, { organisationId: job.organisationId }, ...)` and batch the inserts inside the single transaction.

**C5 — Domain module imports a non-existent infrastructure class; two other new imports are also dangling.** `apps/server/src/modules/contacts/domain/contact.ts:1,17` imports `../infrastructure/pg-contact.repository`, and `contacts.controller.ts:4` imports `../../../observability/logger` — neither file exists anywhere in the tree or its history. Failure mode: this is not a style nit, the module cannot be imported/compiled/executed at all; `npm run build`/any test importing `contact.ts` or the controller throws `Cannot find module` immediately. Fix: either land the missing files in this PR or don't reference them yet; either way this should never have passed a build step before review.

**C6 — Personal data (phone number) written to logs.** `apps/server/src/modules/contacts/http/contacts.controller.ts:13-14` logs `callerPhone` on every search request. Violates INV-12 ("no personal data in logs, metrics, traces, analytics, push"). Failure mode: phone numbers land in the log aggregator/SIEM with normal retention, becoming an uncontrolled PII store outside the audit/retention policy the rest of the system is built around (and outside INV-07/INV-16 style controls). Fix: drop `callerPhone` from the log fields entirely, or hash/truncate it if correlation is genuinely needed, and add a log-scrubbing test.

## High

**H1 — Domain layer depends on a concrete infrastructure class (and instantiates it as a module-level singleton).** `apps/server/src/modules/contacts/domain/contact.ts:1,17`. Violates the module-layering convention (`domain/application/infrastructure/http`, dependency direction inward) called out explicitly in the moin appendix. `export const repository = new PgContactRepository()` runs at import time — any pool/connection setup inside that constructor fires on process boot regardless of use, and every consumer of `domain/contact.ts` (including unit tests of `greetingFor`) now transitively pulls in a Postgres client. Fix: define a `ContactRepository` port/interface in `domain/`, have `infrastructure/pg-contact.repository.ts` implement it, and inject the concrete instance at the composition root (http/job entry points), not from inside `domain/`.

**H2 — HTTP controller talks to Postgres directly, skipping any service/repository layer.** `apps/server/src/modules/contacts/http/contacts.controller.ts:15-16` builds and runs raw SQL from the `http/` layer. This is the routes→DB-directly anti-pattern the layering convention exists to prevent: the same query-construction logic now has to be duplicated or diverges from whatever `PgContactRepository` (referenced but missing) is supposed to own, and there's no place to unit-test the search logic without spinning up Fastify. Fix: move the query into a repository method (e.g. `ContactRepository.searchByName(orgCtx, q)`), have the controller only translate HTTP↔domain.

**H3 — No idempotency key on outbound Stripe call.** `packages/integrations/src/stripe.ts:4-10`. `.claude/rules/integrations.md` explicitly requires idempotency keys on outbound side effects (INV-11). Failure mode: a timeout/retry on `createCustomer` (network blip, client retry, at-least-once queue redelivery) creates two Stripe customer records for one signup, and everything downstream that assumes one Stripe customer per org (billing reconciliation, INV-20) now has to de-dupe after the fact. Fix: pass `Idempotency-Key` header derived from a stable business key (e.g. organisation id) on every mutating Stripe call.

**H4 — Stripe adapter doesn't check response status before treating the body as success.** `packages/integrations/src/stripe.ts:9-10`. `response.json()` is returned unconditionally; a 4xx/5xx from Stripe (bad email, rate limit, auth failure once the key is rotated) is silently returned to the caller as if it were a customer object. This is exactly the "boundary fails to translate errors into a clean response" pattern the review kit flags. Fix: check `response.ok`, throw/translate a typed error on failure, and let the HTTP boundary (not this adapter) decide the client-facing shape.

**H5 — Tenant-specific business logic hardcoded in shared domain code.** `apps/server/src/modules/contacts/domain/contact.ts:11-13` special-cases the string `"Gurlitt"`. Directly violates INV-18 ("no tenant-specific code paths do not exist"). Failure mode: every new customer with custom-greeting requirements requires another code branch and a deploy, tenant behavior lives in `git blame` instead of tenant config data, and this is the first crack that turns into a maintenance/compliance problem once there are a dozen such tenants. Fix: move the greeting template into per-tenant configuration/data (e.g. a `tenant_settings` row), keep `greetingFor` tenant-agnostic.

## Medium

**M1 — Cross-package deep relative import instead of a workspace package boundary.** `apps/server/src/modules/contacts/http/contacts.controller.ts:3` imports `../../../../../../packages/db/src/tenant` by relative path six levels up. No `pnpm-workspace.yaml`/`package.json`/`tsconfig` exists yet in this tree to enforce a package alias, so this isn't broken today, but it reaches into another package's `src/` directly, bypassing whatever public surface `packages/db` is meant to expose once workspace tooling lands. Fix: once P02.02 workspace scaffolding exists, replace with the workspace specifier (e.g. `@moin/db`) and export `withTenant` from the package's `index.ts`, not its internal `src` path.

**M2 — Import job inserts one row at a time in an unbounded loop with no batching or partial-failure handling.** `apps/server/src/modules/contacts/jobs/import-contacts.job.ts:11-17`. A "nightly CSV import" implies potentially large batches; sequential awaited single-row inserts are slow, and a failure on row 500 of 10,000 (after fixing C4, inside one transaction) rolls back everything already inserted with no partial-progress checkpoint, no per-row error isolation, and no idempotency guard against re-running the same file (INV-11 applies to internal retries too, not just external providers). Fix: batch inserts (multi-row `INSERT ... VALUES`), and key the job run so re-running the same import file doesn't duplicate contacts.

**M3 — No audit event on contact creation.** `apps/server/src/modules/contacts/jobs/import-contacts.job.ts` performs a business mutation (contact insert) with no corresponding append-only audit event, per INV-10. Fix: emit an audit event per insert (or per batch) alongside the row write, in the same transaction.
